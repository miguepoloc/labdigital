## §20. Anti-patterns and lessons learned — sourced, not hypothetical

| Anti-pattern | Where it was found | What this standard does instead |
|---|---|---|
| Domain events recorded, never drained | `sona-sso-backend` — `pull_events()` defined, never called | A recorded event without a drain point is review-blocking; the outbox is the mandatory drain point |
| Publish-after-commit with no durability guarantee | `sona` — event lost if the process dies between commit and publish | Outbox row written in the same transaction as the aggregate |
| No idempotency layer for event consumers | `sona` — Standard SQS, no dedup table, `BaseEvent.attempts` fields present but unread | The same `idempotency_keys` table used for HTTP mutations + `idempotence_key()`, mandatory on every event handler |
| Three coexisting generations of "shared" code | `sona` — `shared_package`→`sona_common`→`common`, all three still attached to every Lambda | Exactly one global `commons/`, extend it, never fork it |
| UoW subclass per Lambda composition root | `sona-sso-backend` — an ad hoc matrix, flagged as unresolved in its own `CLAUDE.md` | One generic `UnitOfWork` with a repository registry |
| Orchestrator reaching past services into aggregates/repos | Not found in `bold` (its orchestrators get this right) | Enforced by import-linter contract 6, not just written down |
| `datetime` columns instead of epoch integers | Not found in the reference codebases (they already avoid it) | `PosixTime` + `BigInteger` everywhere |
| Import-linter contracts applied inconsistently across contexts | `sona-sso-backend` — only 2 of 4 contexts had the layering contract | Contract generation templated per new subcontext |
| A 7,499-line "god aggregate" | `bold`'s core `Deposit` aggregate, ~50 channels' worth of limits in one class | Aggregates stay narrow; a 40th enum member on one aggregate is the signal to split, not a feature request |
| In-memory rate limiting under Lambda | `sona`'s `sona_common.middleware.RateLimitingMiddleware` — a plain dict, broken across ephemeral/concurrent containers | Rate limiting belongs at API Gateway or a distributed store, never in-process state |
| Two parallel JWT mechanisms mid-migration | `sona` — legacy HS256 custom-authorizer vs. new RS256, both live | Document only the target; no legacy path to carry |
| Reaching into a value object's internal field to reimplement behavior it already has | `sona-sso-backend`'s own `entrypoints/cron/check_cert_expiry.py` — compares `.microseconds` by hand instead of using `PosixTime.__lt__` | Domain/application code calls the VO's own methods; the ORM mapper is the one authorized exception |
| Event-consumer boilerplate hand-rolled per entrypoint file, no dispatch table | Not found in `bold`/`sona` (both centralize it) | `commons.adapters.sqs.process_sqs_event`, called once per event entrypoint |
| Two hand-maintained mappings (string→class for parsing, class→handler for dispatch) that can silently drift apart | `sona`'s real `event_map`/`event_handlers` pair — `sona`'s own troubleshooting notes list "unmapped event names" as a recurring incident | One `EventConsumer` registration list, keyed by a *computed* `event_type` field that cannot drift from the class it names |
| Every event handler individually responsible for remembering its own idempotency wrapper | `bold`'s own handlers — each opens the transaction and catches the duplicate error itself | The dispatcher wraps the common case automatically; only handlers needing I/O before their write remain responsible by hand |
| No optimistic concurrency control — two concurrent writes to the same aggregate silently overwrite each other | Not found in `bold` (it has real version checking via DynamoDB conditional writes) | `AggregateRoot.version` + SQLAlchemy's native `version_id_col`, raising `ConcurrentModificationError` on a lost race |
| Contract 6 read literally as "never import a sibling subcontext's `domain/` at all" — even a typed ID/value object used only to type-hint a pass-through parameter | Surfaced by this skill's own eval benchmark (iteration 1): a correct, benchmark-passing orchestrator run imported `domain.model.value_objects` for typing and had no rule covering whether that was allowed | `enforcement-and-style.md` §16 contract 6 now carves out `value_objects` explicitly (typing only), keeping `aggregate`/`events`/`rules`/`adapters` strictly off-limits |
| `self.updated_at = PosixTime.now()` repeated inline at the end of every command method | `bold` — this exact line appears in nearly every aggregate's command methods, never generalized | `AggregateRoot.touch()`, one base-class method, called instead of repeating the assignment (`domain-and-application.md` §5.3a) |
| A status field updated by scattered `if status is not X: raise; self.status = Y` checks per command, instead of one declared table of legal transitions | Not found missing in `bold` (its real `_change_status` + a transitions dict already does this) — flagged because an earlier draft of *this* standard's own template `Order` aggregate didn't, despite citing bold's pattern elsewhere | A module-level `_ORDER_STATUS_TRANSITIONS` dict + a private `_transition_status` choke point, the same shape as bold's `bancolombia_cardless_cashout/aggregate.py` (`domain-and-application.md` §5.3a) |
| External I/O (a port call) made *inside* an already-open `with uow.transaction():` block | An earlier draft of this standard's own template `services/orders.py::confirm_order` — its sibling `create_order` already fetched external data before opening the transaction, but `confirm_order` didn't | `persistence-and-concurrency.md` §8's "No I/O inside an open transaction" rule — the fetch moves to whichever function opens the *outermost* transaction, since a nested `uow.transaction()` call is a no-op |
| A service function silently constructing its own default adapter (`port = pricing_port or pricing_adapter.HttpPricingAdapter()`) instead of requiring the port as a parameter | An earlier draft of this standard's own `services/orders.py` — bold's real `x or DefaultAdapter()` pattern only appears inside a class's own `__init__`, never inline in a plain service function called per request | `entrypoints-and-orchestration.md` §9.1 — the entrypoint is the composition root; a private `_get_pricing_port()` factory there, never a fallback inside the service |
| Two independent bounded contexts (`orders`, `stock`) routed through one combined `entrypoints/web/public.py` file/Lambda | An earlier draft of this standard's own template — contradicted its own Order+Stock divergence reasoning and `sona-sso-backend`'s real practice of one router file per subcontext | `entrypoints-and-orchestration.md` §9.1 — one file per subcontext, each its own `app`/`mangum.Mangum(app)` |
| A bare integer HTTP status code (`status_code=201`) instead of `fastapi.status.HTTP_201_CREATED` | An earlier draft of this standard's own template, in three call sites | `enforcement-and-style.md` §17.1 — `from fastapi import status`, then `status.HTTP_201_CREATED`, matching every real `sona-sso-backend` router file |
| An HTTP adapter method with no retry on transient network failures, parsing `response.json()` by raw dict-key access instead of a typed response schema | An earlier draft of this standard's own `pricing_adapter.py`/`user_profile_adapter.py` — bold's real `bancolombia_cardless_cashout/adapter.py` has both `@backoff.on_exception(...)` and a typed-DTO parsing step first | `entrypoints-and-orchestration.md` §10.2a — `backoff.on_exception(backoff.expo, ..., jitter=backoff.full_jitter, max_tries=3)` + a `_*ResponseDTO(pydantic.BaseModel)` parsed before conversion to the domain type |
| `OrderId(value_objects.UuidV7Id)`, contradicting this same standard's own rule ("use `HumanFriendlyId` only when the ID is genuinely user-facing") in the very example meant to illustrate it | An earlier draft of this standard's own template — `Order` is exactly the "a customer reads this off a receipt" case bold's real `LoanId`/`CashoutId` (both `HumanFriendlyId`) demonstrate | `domain-and-application.md` §5.2 — `OrderId(value_objects.HumanFriendlyId)`; `StockId` correctly stays `UuidV7Id` |
| `identity.users.UserId(value_objects.UuidV7Id)`, reasoned only against bold's fintech aggregates, never checked against `sona-sso-backend`'s own identity aggregates — the actually comparable precedent | An earlier draft of this standard's own template — `sona-sso-backend`'s real `ConsoleUserId`/`OrganizationId`/`SsoConnectionId` are all `HumanFriendlyId` | `domain-and-application.md` §5.2 — `UserId(value_objects.HumanFriendlyId)`; `commerce.orders.CustomerId` follows it (mirrors `UserId`'s real value) — not caught by any tool, `CustomerId(value: uuid.UUID)` type-checked fine right up until a real `HumanFriendlyId` string hit `uuid.UUID(...)` and raised `ValueError` at runtime |
| A hand-rolled email regex instead of `pydantic.EmailStr` — looser than the real spec (accepts consecutive dots, `a..b@sub..domain.com`) | An earlier draft of this standard's own `identity.users.value_objects.Email` — bold uses `pydantic.EmailStr` directly on over a dozen real DTOs/models | `enforcement-and-style.md` §17.3 — `EmailStr`'s validation wrapped in a `field_validator` that re-raises this codebase's own `exceptions.ValidationError`, so a malformed email still surfaces as the established 422 |
| A top-level orchestrator (`deactivate_user_cascade.py`) that unconditionally forwarded to exactly one service function — a Middle Man, not real cross-product orchestration, presented as §10.3's own flagship example | An earlier draft of this standard's own template — caught by asking "why is this an orchestrator if it only calls one aggregate?", not by any tool | `entrypoints-and-orchestration.md` §10.3 — deleted; the entrypoint calls `auth.deactivate_user` directly (§10.1); `orchestrators/` stays empty in this golden path, a real extension point rather than a forced example |
| One `Repository[T].put()` covering both insert and update via `session.merge(...)`, unable to express collision-retry on a `HumanFriendlyId` insert at all | An earlier draft of this standard's own template — `sona-sso-backend`'s real `OrganizationRepository` has separate `add()`/`update()` methods, never one unified `put` | `persistence-and-concurrency.md` §7 — `Repository[T].add`/`.update`, matching the real interface |
| A `pydantic-settings` dependency declared and never used — hand-rolled `os.environ.get(...)` reads in `commons/adapters/settings.py` instead, plus `os.environ[...]` scattered directly in two HTTP adapters and an entrypoint, `INTERNAL_API_KEY` duplicated across two of them | An earlier draft of this standard's own template — `sona-sso-backend`'s real `commons/settings.py` is `pydantic_settings.BaseSettings`, one class, one vocabulary | `shared-kernel-and-testing.md` — `Settings(pydantic_settings.BaseSettings)`, every env var validated once at `get_settings()` |
| A collision-retry helper that calls plain `session.rollback()` on a failed insert attempt, rolling back the *entire* outer transaction instead of just the one failed insert | An earlier draft of this standard's own `insert_with_id_retry` — `sona-sso-backend`'s real version uses `session.begin_nested()` (a SAVEPOINT) specifically to scope the rollback | `persistence-and-concurrency.md` §7.1 — `with session.begin_nested(): ...` around each retry attempt |
| Recorded events drained and published by a hand-called `_publish_events()` helper in every `services/*.py` function — easy to forget on a new use case | An earlier draft of this standard's own template, in every subcontext's services module — contradicts bold's documented lifecycle ("`save(aggregate)` calls `uow.publish(event)` inside a transaction") | `persistence-and-concurrency.md` §7 — `Repository[T].add`/`.update` publish internally; a service can no longer forget |
| An orchestrator comparing a DTO's status field against a raw string (`order.status == "confirmed"`) instead of asking a named question | An earlier draft of this standard's own `services/cancel_order_orchestrator.py` | §22.1 below — Tell, Don't Ask: `Order.had_reserved_stock`, a property captured before mutating and threaded through the DTO |
| `uow.repo(aggregate.X)` resolved one line *before* `with uow.transaction():` opens, instead of as the first line inside it | An earlier draft of this standard's own `services/orders.py`/`services/stock.py`/`services/auth.py` — `UnitOfWork.repo` reads `UnitOfWork.session`, which raises `RuntimeError` until a transaction is open | `domain-and-application.md` §6 — the repository is always resolved as the first statement inside the `with` block |
| `uow.repo(aggregate.X)` called twice in one function instead of once, cached in a local variable | An earlier draft of this standard's own `services/orders.py`/`services/auth.py` | `domain-and-application.md` §6 — resolve once per function, reuse the local variable |
| DTO output fields typed as bare `str` for what is really an enum (`status: str`, `currency: str`), populated via `.value` | An earlier draft of this standard's own `OrderOutputDTO`/`OrderLineOutputDTO` | `domain-and-application.md` §5.2/§6 — `status: value_objects.OrderStatus`, `currency: money.Currencies`; `StrEnum` still serializes to a plain string over the wire |
| Reconstructing a value object from a plain scalar via `Foo.model_validate({"value": x})` in some call sites and direct `Foo(value=x)` in others, with no reasoning behind which got which | An earlier draft of this standard's own template — 6 call sites used `model_validate`, 10 others in the same codebase already used direct construction correctly | `enforcement-and-style.md` §17.3 — always direct keyword construction for a single already-known scalar; `model_validate` is for an already-dict-shaped multi-field payload |
| `# type: ignore` reached for before the actual type was fixed — an untyped `sns_client: object`, a registry typed `type[Repository[Any]]` when the real contract was a `Callable`, a `Protocol` missing one attribute it could have declared, a union-of-different-arity-callables dispatched by runtime introspection | An earlier draft of this standard's own template — 4 separate ignores, each fixable | `enforcement-and-style.md` §2.1 — `mypy_boto3_sns.client.SNSClient`, `Callable[[Session], Repository[Any]]`, `id: str` on the Protocol, and splitting `EventConsumer.handle` into two mutually-exclusive fields; the one ignore that's a genuine, verified mypy/pydantic limitation stays, narrowly scoped |
| `UserProfile` (a port's return type) made a `dataclass`, reasoning from `EventConsumer`'s dataclass rule without re-checking it against the actually comparable bold precedent | An earlier draft of this standard's own template — bold's real `AuthResponseBody` (also adapter-output data handed to application code) is `base_types.ValueObject` — Pydantic, not a dataclass | `enforcement-and-style.md` §17.3 — `UserProfile(value_objects.ValueObject)`; the dividing line is whether the data was ever assembled from parsed external input, not whether this line re-validates it |
| A `StrEnum`'s member values typed out by hand (`PENDING = "pending"`, `COP = "COP"`) when the value is just the member name, upper- or lowercased | Not a bug, a missed simplification, in two stages: `OrderStatus` (lowercase) was fixed with plain `StrEnum.auto()` first; `Currencies` (uppercase) was left explicit with a comment saying `auto()` "can't" cover it, until a prior project's real `UpperStrEnum` was pointed out | `enforcement-and-style.md` §17.3 — `PENDING = enum.auto()` on plain `enum.StrEnum` for lowercase; `commons/domain/enums.py`'s `UpperStrEnum` (overrides `_generate_next_value_` to return the name unchanged) + `COP = enum.auto()` for uppercase — two small, symmetric bases, not one rule with an unhandled half |

Some of these were caught in an earlier draft of the standard itself, not just in the three
source codebases — this table stays honest about that too, on the theory that a rule is more
credible with its own history attached than presented as received wisdom.

## §22. Design principles and code smells reference

Terminology and refactoring techniques below follow the standard classification (Fowler /
refactoring.guru). When you're about to write code for this standard and something feels
off, check here first — the smell probably has a name and a known fix.

### §22.1 Code smells actively designed against

| Smell | Refactoring technique | Where this standard applies it |
|---|---|---|
| **Message Chains** (`a.getB().getC().getD()` — the smell name for what's commonly called a Law of Demeter violation) | Hide Delegate | Domain and application code call a value object's own methods (`PosixTime.__lt__`, `Money.compare`) instead of chaining into `.microseconds`/`.value`. The ORM mapper's `_to_orm`/`_to_entity` (`persistence-and-concurrency.md`) is the one authorized exception — a Data Mapper's whole job is bridging two representations, not a chain a caller stumbled into. |
| **Feature Envy** (a method more interested in another class's data than its own) | Move Method | `Order.total` is a method *on* `Order`, computed from `self.lines` — an external `OrderTotalCalculator` reaching into `order.lines` from outside would be textbook Feature Envy over data `Order` already owns. |
| **Inappropriate Intimacy** (two classes reaching into each other's internals instead of going through a public contract) | Move Method / encapsulate the state | An orchestrator calling `uow.repo(Stock)` and mutating `stock.available_quantity` directly — instead of calling `stock_service.reserve_stock(...)` — is this smell, precisely: reaching past `Stock`'s own service into its internals. Import-linter contract 6 (`enforcement-and-style.md`) makes it a build failure, not just a code-review catch. |
| **Switch Statements** (branching repeatedly on an object's "type") | Replace Conditional with Polymorphism | The HTTP-status-mapping table and the `EventConsumer` registry are deliberate **dictionary-dispatch**, not `if/elif` chains keyed on event or error type. Narrow, named exceptions per invalid transition are the same idea one level up: `InsufficientStockError` is its own class specifically so nothing downstream needs a `match error.code:` block to know what happened. |
| **Refused Bequest** (a subclass inherits behavior it doesn't want, and overrides it just to reject it) | Reorganize the hierarchy | Cited as the reason `commons.domain.entities.Entity[IdT]` stays minimal (identity + timestamps only) rather than a fatter base class every aggregate would have to override away unwanted behavior from. |
| **Tell, Don't Ask** (a caller inspects an object's state to make a decision the object itself should make) | Move the decision into a query method on the object that owns the state | `Order.had_reserved_stock` (`domain-and-application.md` §5.3a): `services/cancel_order_orchestrator.py` asks `cancelled_order.had_reserved_stock` — a named question `Order` itself answers (`self.status is OrderStatus.CONFIRMED`) — instead of comparing `order.status == "confirmed"` against a magic string itself. The orchestrator tells `orders.cancel_order` to cancel and asks what happened; it never re-derives the answer from raw state it peeked at externally. |

### §22.2 A smell this standard deliberately does *not* over-correct: Middle Man

**Middle Man** — a class whose methods only forward to another object, adding no behavior —
is the failure mode on the *other* side of Hide Delegate and Inappropriate Intimacy: fixing
one of those two by wrapping every call in a pass-through layer recreates this one. Two
concrete guardrails exist for exactly this reason:

- A single-aggregate use case is called directly, with **no** orchestrator wrapping it "for
  symmetry" (`entrypoints-and-orchestration.md` §10.1). An orchestrator that only forwards
  one call to one service function, unconditionally, is a Middle Man — delete it. Not
  hypothetical: §10.3's own flagship example, an earlier draft's
  `orchestrators/deactivate_user_cascade.py`, was exactly this — caught by asking "why is
  this an orchestrator if it only calls one aggregate?", deleted once traced through.
- `DefaultStockRepository` implements `Repository[T]` directly; there is no second "service"
  layer interposed between the repository and its one caller that would do nothing but
  rename `add`/`update`/`get_by_sku` to something else. A layer earns its place by owning a rule, a
  translation, or a transaction boundary — not by existing between two other layers.

### §22.3 SOLID principles this architecture is built from

| Principle | Where |
|---|---|
| **Single Responsibility** | The whole `domain/model/` → `domain/services/` → `services/` → `adapters/` → `entrypoints/` split (`../SKILL.md`'s bounded-context recipe) is one responsibility per layer: business rules, cross-aggregate pure logic, use-case orchestration, persistence translation, transport. |
| **Open/Closed** | New bounded contexts, new event consumers (the `EventConsumer` registry), new external adapters are all *additions* to a list/registry, never edits to existing dispatch code. |
| **Liskov Substitution** | Narrowing `id: EntityId` to `id: StockId` in a subclass is the same category of violation as the canonical car-hierarchy example (a subclass changing a method's return type breaks every caller that trusted the base type's contract) — PEP 695 generics (`Entity[IdT]`) are the fix that requires no exception to the rule anywhere. See `domain-and-application.md` §5.1 for the full reasoning. |
| **Interface Segregation** | Every port is narrow and single-purpose (`PricingPort` does pricing, nothing else) — never one fat `ExternalServicesPort` a subcontext would have to depend on in full to use one method of. |
| **Dependency Inversion** | The entire Ports & Adapters shape *is* DIP: `orders/services/orders.py` (high-level) depends on `PricingPort` (an abstraction it owns), never on `orders/adapters/pricing_adapter.py` (the low-level detail) directly — structurally identical to a `NotificationService` depending on an abstract `Notifier` rather than a concrete `EmailNotifier`. Swapping the concrete pricing adapter never touches the service that uses it, by construction. |
